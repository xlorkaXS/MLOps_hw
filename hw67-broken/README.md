# ДЗ 6+7. От эксперимента до проверенного адаптера

Это **одна домашняя работа** по двум лекциям. Продолжайте свой проект
ДЗ 4-5. Один поиск, один кандидат для полной оценки, один комплект сдачи.

## Что уже есть и что сделать

- `src/`, `compose.yaml`: знакомый старт ДЗ 6 с четырьмя дефектами.
  Исправьте смешивание runs, потерю артефактов, отсутствие версии данных
  и обход порога по loss. Зафиксируйте разбор в `docs/defects.md`.
- `evaluation/cli.py`, `contract.py`: готовая обвязка оценки и выпуска.
- `evaluation/solution.py`: **две функции TODO**, которые нужно написать:
  подсчёт качества `score` и правило допуска `quality_gate`.
- `tests/test_eval.py`: тесты этих функций без модели, GPU и сервера.
- `examples/`: иллюстрации формата, **не готовый golden set**.

## Один маршрут

Python 3.12, uv, Docker Compose v2, Git. На Windows используйте WSL/Git Bash
или выполните команды Makefile по одной. UI: http://127.0.0.1:5006.
Как и в старом ДЗ 6, сервер использует compose project `mlops-hw6`.
Не запускайте второй экземпляр сервера на том же порту.

1. Положите свои тензоры ДЗ 4 в `data/tokenized/`, настройте `params.yaml`,
   сохраните код в Git. Имя модели должно совпадать с токенизацией.
2. Исправьте четыре дефекта части A. Напишите две функции оценки;
   `make check-eval` можно выполнять сразу, без обучения.
3. Соберите свои данные проверки и настройте `evaluation/params.json`
   по инструкции `EVALUATION.md`. Примеры из `examples/` замените своей темой.
4. Выполните:

```bash
uv sync --frozen
make check-eval          # тесты двух функций; не обучает
make up
make sweep              # один поиск: 6 конфигураций x 4 шага
make report             # docs/comparison.csv из MLflow
make candidate          # loss-порог -> версия реестра с alias candidate
make baseline-init      # один раз: закрепить исходную модель
make evaluate           # реальные ответы baseline и одного кандидата
make eval               # только правило качества по сохранённым ответам
make check-negative     # копия ответов испорчена -> ожидается отказ
make promote            # только после PASS: champion -> проверенная версия
make check-storage
make check              # 9 проверок MLflow/загрузки; проверяет alias candidate
make check-all          # эти 9 проверок + тесты оценки
```

`make evaluate` может записать неуспешные ответы; `make eval` обязан
отказать при ошибке генерации, несовместимости или регрессии. Не подавляйте
ненулевой код возврата и не меняйте порог после просмотра результата.
`make promote` сам повторно проверяет качество, поэтому его нельзя
использовать для обхода отказа. Для штатного выпуска используйте именно
эту команду; старый `src.promote` обслуживает регистрацию части A.

**Отказ по качеству - допустимый итог работы.** Не подменяйте метрики:
оставьте `champion` прежним (или не создавайте, если его ещё не было),
приложите отчёт и объясните причину. Alias `candidate` остаётся доступным,
поэтому все девять проверок хранения и загрузки можно выполнить и при
непринятом кандидате. Увеличивать бюджет обучения ради оценки не обязательно.

`make baseline-update` используется только после принятия кандидата.
Он явно делает принятую версию новой точкой отсчёта и сохраняет старую
в `evaluation/baseline-history/`. Последующие оценки прогоняют обе версии
заново на одном протоколе. Автоматически после `evaluate` baseline не меняется.

## Если ДЗ 6 уже сделано

Не начинайте проект заново и не обучайте шесть моделей ещё раз без причины.
Перенесите из архива `evaluation/`, `examples/`, `EVALUATION.md`, тест оценки
и новые команды Makefile в свой исправленный проект. В проверке загрузки
используйте alias `candidate`, как в этом архиве. Код `src/`, train/val и
старый `params.yaml` оставьте прежними: их хеши должны совпадать с runs.
`make candidate` переиспользует законченный sweep и создаёт отдельный alias.
Изменения только в `evaluation/` не требуют повторного обучения.
Если код обучения, его конфиг или train/val действительно изменились,
сравнение нужно пересобрать честно.

## Что сдавать один раз

- Один Git-репозиторий и коммит; данные проверки под DVC из вашего проекта.
- `docs/comparison.csv`, `docs/defects.md` и **один** `docs/conclusion.md`:
  выбор по loss, сравнение ответов, срезы, новые ошибки, решение о выпуске.
- Версии golden/behavioral/train-index, `evaluation/params.json`,
  `evaluation/baseline.json`; минимум 50 golden-примеров и 3 behavioral-кейса.
- `metrics/*-outputs.json`, `*-eval.json`, `eval-diff.json`,
  `quality-gate.json`, `negative-gate.json`, `storage-check.json` и ссылки
  на соответствующие runs в MLflow. Сохраните их в отдельном каталоге
  сдачи/прикрепите к отчёту, если ваш `.gitignore` исключает `metrics/`.
- Одно видео 5-8 минут: шесть runs, candidate, результаты оценки,
  отрицательная проверка, состояние champion, проверка хранения и тесты.

Веса, тензоры обучения, `.venv`, volumes и секреты не включайте в архив
сдачи и Git. Тесты не ослабляйте; при изменении приложите diff.
Отпечаток считается по всем файлам `tests/` и показан в HTML задания.
