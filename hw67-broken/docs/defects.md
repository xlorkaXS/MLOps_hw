# Четыре дефекта учёта экспериментов

## 1. Разные кандидаты записывались в общий run

В исходном sweep один вложенный all-candidates охватывал весь цикл. Параметры логировались только для первого кандидата, а метрики и модель следующих перезаписывали общую историю. Сравнение шести конфигураций становилось недостоверным. Исправление: start_run с nested=True находится внутри цикла; каждый кандидат получает собственные параметры, кривые, образцы генерации и модельный пакет. Родитель содержит только сводку. Доказательство — шесть отдельных FINISHED runs, проверка 1 и соответствие реальных конфигураций кривым в проверках 3–4. Измеренные run id приводятся в comparison.csv.

## 2. Файлы терялись при замене контейнера

PostgreSQL имел volume, а /mlartifacts оставался в записываемом слое контейнера MLflow. Метаданные могли пережить пересоздание, хотя сами файлы уже исчезли. Добавлено именованное хранилище artifacts:/mlartifacts. Проверка check-storage загружает уникальный probe, пересоздаёт только сервис mlflow без удаления базы и volumes, затем скачивает файл и сравнивает SHA256. Доказательство сохраняется в metrics/storage-check.json; проверка 8 дополнительно скачивает тот же файл. Обычный down не удаляет volumes; down -v не используется.

## 3. У запусков не было версий train и val

provenance вычислял SHA256 тензоров, но main удалял ключи data_* перед передачей дочерним runs. По одному git SHA нельзя определить содержимое некоммитимых .pt. Фильтрация удалена: каждый кандидат получает data_train_sha256 и data_val_sha256, вместе с code_sha256, config_sha256, git_sha и закреплённой ревизией базы. Входы побайтно совпадают с ДЗ4; полный train-index связывается с исходным JSONL и всеми id тензоров в evaluation.prepare_data. Подтверждение — data-provenance.json, DVC-указатели и проверка 2. Изменение данных теперь запрещает повторное использование прежнего sweep.

## 4. Регистрация обходила loss-порог

Функция gate существовала, но promote только вычислял отношение и немедленно менял реестр. Даже нулевой порог не останавливал регистрацию. Теперь promote сначала вызывает gate(run, threshold). Проверяются FINISHED, конечность обеих метрик и порога, положительность base loss и условие val/base <= max_ratio. Только после успеха вызывается register_model и назначается alias. Проверка 6 передаёт порог 0.0 и требует отказа до мутации реестра. Alias candidate отделён от champion: последний меняется только через evaluation.cli.release после повторной полной проверки качества. Отрицательная проверка части B меняет копию ответов, не реальные веса.

Тесты из комплекта не изменяются. Их исходный отпечаток c42ac7788026 проверяется отдельно. Реальные измерения и итог качества сведены в conclusion.md, а не заменены результатами синтетических фикстур.
